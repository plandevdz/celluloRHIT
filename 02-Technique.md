# 02 | Cahier des charges technique — application web et serveur Rust

## T01. Architecture de référence
Décision retenue pour V1 (révision du 12/11/2026, remplace le client Windows natif) : **application web** servie par le serveur central, utilisée depuis un navigateur récent (Edge, Chrome, Firefox) sur les PC habilités. Aucun logiciel à installer sur les postes. Serveur : API et worker Rust (Axum/Tokio), PostgreSQL (SQLx), interface React + TypeScript (Vite) compilée en fichiers statiques et servie par l’API, reverse proxy HTTPS Caddy. L’ensemble tourne en **conteneurs Docker (docker compose)** sur le serveur Debian 13 de l’entreprise et est joint par son adresse IP (ou un nom DNS interne) : `https://<IP-du-serveur>/`. Aucune obligation Kubernetes ou partage SMB.

Chaque navigateur communique uniquement avec le proxy sur HTTPS/443 via LAN ou VPN de site ; le port 80 redirige vers 443. Le serveur central assure règles métier, autorisations, données, PDF, journal et envois Microsoft. PostgreSQL n’est joignable que sur le réseau Docker interne, jamais publié sur l’hôte ; l’API n’est publiée que derrière le proxy. Ni clé Graph ni mot de passe SQL côté navigateur. Les opérateurs peuvent se servir de l’application sans identité Microsoft. Ne jamais écrire dans Intelix ou Xena en V1 : les tâches consignent le travail des opérateurs.

Organisation du dépôt : `crates/domain` (invariants purs, testés sans base), `crates/server` (commandes et transactions, API, worker, adaptateurs PostgreSQL et Microsoft, PDF), `migrations` (SQL versionné), `web` (interface), `deploy` (compose, Caddy, exemple de configuration sans secret). Contrat versionné /api/v1 ; DTO distincts des lignes de base. Dépendances et toolchain verrouillées (Cargo.lock, package-lock.json). Une seule image Docker multi-étapes : compilation de l’interface, compilation Rust, image Debian slim d’exécution non-root. Le même binaire démarre l’API (`serve`) ou le worker (`worker`), en deux services distincts. Livrer image, migrations SQL, fichier compose, exemple de configuration, procédure de mise à niveau et test de restauration.

## T02. Contrat de données
Voir 04-Donnees.md : noms de tables logiques de référence pour les migrations. PostgreSQL porte les contraintes de concurrence et d’unicité. IDs internes stables, références publiques ONB/MUT/OFF/DEM sur une séquence serveur ; jamais MAX+1. Matricule texte nullable, index unique partiel sur valeur normalisée non vide. Nom + prénom ne sont pas une clé. Date RH locale distincte des instants de coupure stockés en UTC et présentés en Africa/Algiers. Un salarié peut cumuler plusieurs demandes ponctuelles et une transition de poste ; aucune unicité globale « un seul dossier ouvert par salarié ».

## T03. Commandes API principales
| Commande | Contrat |
|---|---|
| POST /arrivals | RH/Admin, cinq champs requis. Avec Idempotency-Key : créer ou lier la fiche explicitement choisie, créer dossier ouvert, besoins fournis, tâches applicables, avis IT/FORMATION et audit dans une seule transaction. Aucun besoin précis : envoyer l’annonce sans générer un compte ou un actif fictif. |
| POST /cases/{id}/needs | Ajouter/modifier une demande avec version attendue ; conserver l’ancienne préférence et les mouvements existants. Dédupliquer les tâches, notifier seulement les équipes impactées. |
| POST /employees/{id}/requests | DEM autonome ; rattachement facultatif à un dossier antérieur. Ne jamais rouvrir le parent. |
| POST /transfers puis /transfers/{id}/confirm | Comparaison à partir des droits/affectations effectifs ; stocker snapshot et version du poste. Worker applique la cible confirmée à échéance dans une transaction avec verrou, comparaison de version et clé unique d’application. |
| POST /departures puis /departures/{id}/schedule | Date administrative et instant de coupure séparés. Le worker crée/active les tâches, relance et signale les retards ; seule la confirmation humaine enregistre la désactivation externe. Après redémarrage, traiter également les échéances passées. |
| POST /tasks/{id}/claim | Mise à jour conditionnelle sur état libre et rôle autorisé. Un seul gagnant ; HTTP 409 avec détenteur réel pour le second. Utilisateur IT + FORMATION : périmètre cumulé sans tâche dupliquée. |
| POST /handovers ; POST /returns | Verrouiller chaque ressource ou solde, contrôler titulaire, quantités et capacité. Mouvement, lignes, affectations, preuve à produire et événement enregistrés ensemble. Ne pas clore d’autres lignes lors d’un retour partiel. |
| POST /inventories/{id}/scan ; /reconcile | Jeton stable non secret ; lecture via USB/Bluetooth ou saisie manuelle. Rejouer le scan sans doubler les totaux. Pointage et rectification de stock sont deux commandes à droits et traces distincts. |
| POST /personnel-imports/preview puis /commit | Prévisualisation sans écriture métier ; hachage fichier et version des lignes, résultat par ligne, confirmation RH/Admin. Rejeu du même lot sans double création ; aucun événement d’arrivée. |
| POST /cases/{id}/close | Retourner les points non résolus et exceptions admissibles. Une action compensatrice journalisée corrige un mouvement réel ; elle n’efface pas la preuve. |

Même clé et payload = même résultat ; clé réutilisée pour un autre contenu = refus. Contrôle de version sur toute saisie concurrente ; 403 hors périmètre, 409/412 pour conflit, 422 avec champ/action concernée. Aucun appel Graph ou impression dans la transaction SQL. Les événements portent un identifiant de corrélation.

## T04. Identités, autorisations et secrets
Base V1 : comptes nominatifs internes créés par Admin, activation initiale à usage unique, mot de passe haché Argon2id avec paramètres calibrés sur le serveur, temporisation des tentatives et réinitialisation auditée. Pas d’accès anonyme sur le LAN. Prévoir MFA pour comptes privilégiés et révocation des sessions lors d’une désactivation. Authentification AD/Entra optionnelle plus tard ; jamais prérequis pour un utilisateur cPanel. Session courte renouvelable côté serveur : jeton aléatoire dans un cookie `HttpOnly`, `Secure`, `SameSite=Strict`, seul son hachage est stocké en base ; expiration sur inactivité et durée maximale, révocation à la déconnexion ou à la désactivation. Aucun jeton dans le stockage local du navigateur. En-têtes de sécurité (CSP stricte, pas d’iframe, pas de cache sur les réponses API).

Autoriser côté API à chaque requête selon rôle, équipe, attribution et salarié concerné, y compris export et téléchargement. Les techniciens voient besoins IT, identité utile et site, pas les pièces RH. TLS avec CA approuvée sur les PC, sans contournement des erreurs de certificat. Services non-root dédiés, droits minimaux sur fichiers et SQL, secrets hors dépôt/image Docker/logs (fichier `.env` ou secrets Docker sur le serveur), rotation et procédure de révocation. Données fictives et comptes distincts en test. Durées de conservation du dossier, PDF et journaux à valider RH/DSI avant production.

## T05. Exchange Online et notifications
Hypothèse à confirmer au raccordement : la boîte dédiée est **Exchange Online**. Si elle est Exchange sur site, revoir l’adaptateur avec l’administrateur ; ne pas déployer la configuration Graph ci-dessous telle quelle.

1. L’admin crée la boîte d’expédition. Paramètres du serveur : tenant_id, client_id, identifiant de la boîte et référence au certificat ; l’adresse n’est pas compilée dans le client. Enregistrer un principal applicatif, installer sa clé privée uniquement sur le serveur et prévoir son renouvellement.
2. Utiliser OAuth2 client credentials avec certificat et Microsoft Graph POST /users/{boite}/sendMail. Autoriser l’envoi avec le rôle Exchange « Application Mail.Send » limité à cette boîte via Application RBAC. Vérifier qu’aucun octroi Entra hors périmètre n’étend les mêmes droits. Test positif sur la boîte dédiée, test négatif sur une seconde boîte. Ne pas demander le mot de passe de la boîte ni les droits de lecture du courrier pour envoyer.
3. Résoudre les destinataires depuis l’annuaire applicatif issu de UtilisateursApp : équipe et rôle actifs, adresse normalisée, doublons éliminés. Pour les formations, relier la session au formateur actif ; sans correspondance, routage à corriger. Grouper les avis d’une équipe pour un dossier. Corps minimal : référence, action, échéance, chemin pour ouvrir le dossier dans l’application. Pas de pièces RH ni de secret dans le mail.
4. Worker indépendant : réclamer un lot par bail SQL, expirer les baux abandonnés, respecter Retry-After pour la limitation ; temporisation exponentielle pour panne transitoire ; erreurs de permissions/destinataires remontées à l’admin. HTTP 202 = accepté par Microsoft, pas preuve de livraison. Si timeout après soumission et résultat indéterminé, marquer À vérifier, ne pas réexpédier aveuglément. Inutile de promettre « exactement une livraison » entre deux systèmes.
5. Console Admin : mode test redirigé vers adresse autorisée, aperçu avant envoi, dernier résultat, nombre de tentatives, reprise motivée. Aucune émission réelle depuis DEV/TEST hors destinataires pilotes autorisés. Mails d’équipe même si l’employé n’a aucune adresse.

## T06. Documents, impression et SharePoint
Produire le PDF côté serveur depuis un modèle versionné et le mouvement figé ; intégrer une police Unicode pour noms et accents ; tester les longues lignes, numéros de série et impression A4. Le navigateur télécharge le PDF après autorisation et l’ouvre dans sa visionneuse pour impression locale. Stocker original et scan séparément, chemins techniques stables (ex. dossiers/ONB-00007/remises/{mouvement}/v1-original.pdf). Fichier uploadé : contrôler taille, signature de format et contenu, quarantaine en cas d’échec ; ne jamais exécuter un fichier reçu.

Adaptateur d’archive séparé de l’identité d’envoi Exchange : permission Graph limitée au site/bibliothèque cible, tester le refus sur un autre site. En cas d’indisponibilité, spool chiffré ou volume protégé local, entrée SQL en attente, hash et reprise après redémarrage ; pas de suppression de la copie locale avant confirmation distante et vérification de l’identifiant. Prévoir sauvegarde du spool et restauration indépendante des documents SharePoint. Les utilisateurs passent par l’API ainsi que les droits d’archive, sans lien public.

## T07. Exploitation et recette technique
- Debian sans GUI avec Docker Engine et le plugin compose ; projet dans /opt/celluloplast (compose + `.env` non versionné, droits 600), données dans des volumes Docker nommés (base, documents/spool, données Caddy). API et worker en services distincts, `restart: unless-stopped`, démarrage après la base (healthcheck). Migrations appliquées au démarrage de l’API. Journalisation structurée sans contenu RH (`docker compose logs`) ; alertes espace disque, âge de sauvegarde, worker arrêté, file trop ancienne, expiration certificats. Horloge synchronisée sur l’hôte.
- TLS : Caddy émet un certificat depuis sa CA interne pour l’IP/le nom du serveur ; l’IT installe le certificat racine de cette CA dans le magasin « Autorités de certification racines de confiance » des PC (GPO ou manuel). Aucun contournement d’avertissement de certificat. Remplaçable par un certificat de la PKI d’entreprise.
- PC serveur unique = arrêt du service lors d’une panne. Proposition pilote : RPO 24 h et RTO 4 h à confirmer. Sauvegarde quotidienne chiffrée hors machine de PostgreSQL, spool, modèles, paramètres et matériel de reprise protégé. Tester sur deuxième machine : restauration base + documents, références, rôles, comparaison des empreintes, contrôle des mails en attente avant remise en service. Mesurer le délai ; si objectif non tenu, revoir matériel et procédure.
- Postes : aucun installateur ; l’IT diffuse l’URL interne (favori) et le certificat racine. L’interface et l’API sont livrées ensemble dans la même image, donc toujours compatibles ; après mise à jour, l’interface détecte la nouvelle version et invite à recharger la page sans perdre la saisie en cours. Mise à niveau : sauvegarde, `docker compose pull`/`build`, `up -d`. Procédure de retour à l’image précédente ; pas de downgrade destructif de schéma improvisé.
- Proposition pilote : 20 sessions simultanées, 10 000 dossiers fictifs, listes paginées ; p95 inférieur à 2 s pour recherche/lecture sur LAN et création d’une arrivée en moins de 3 s hors opérations externes. Mesurer CPU/RAM/disque sur le vieux PC ; une saturation bloque le feu vert production.
- Tests : règles de domaine, intégration sur vraie base isolée, deux affectations concurrentes, redémarrage après commit avant envoi, rejet 403 sur dossier hors périmètre, réseau coupé lors du dépôt du scan, absence de double tâche, refus seconde boîte Exchange, panne archive et restauration. Validation manuelle sur PC Windows avec Edge et Chrome : accès par IP en HTTPS sans avertissement, mise à jour de l’application en cours d’utilisation, impression A4 et réouverture d’un dossier après coupure réseau.

Non renseigné ≠ Non. Aucun envoi et aucune régénération de tâches historiques à l’import. Proposer une décision nominative sur les anomalies, rapprocher les totaux et contrôler par échantillon les relations et PDF. Au gel final : reprise du delta, validation RH/IT, ouverture de l’URL aux utilisateurs, ancienne app en lecture seule. Si échec, revenir à la source précédente avant toute double écriture ; après première saisie réelle, réconcilier les nouvelles opérations avant tout retour.
